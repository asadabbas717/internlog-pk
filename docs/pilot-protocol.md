# Small pilot usability protocol

Prepared 2026-10-21. **Protocol ready; student sessions NOT RUN.** Technical acceptance and owner-reported fixes are recorded separately in [pilot feedback](pilot-feedback.md). This is a usability exercise, not institutional approval, a security certification or evidence of academic credit.

## Before a session

Plan one initial round of 3–5 adult volunteers who self-identify as undergraduate computing students in Pakistan; this is a proposed scope, not an enrollment count. Allow roughly 20–30 minutes per session and use the participant's preferred way of navigating. Include intended Android/iOS browsers when available; never substitute emulation for a physical-device result.

The facilitator records the actual build commit, date, browser/OS family and test mode (local development, production preview or deployed HTTPS). Confirm passing quality gates for that build and review [release limitations](release.md). Run the synthetic save/reload, backup/restore and print tasks once on the chosen device before involving a volunteer. A blocked recovery or data-safety check stops the session until resolved.

Use a dedicated empty test origin or browser profile. If existing personal records appear, stop and switch to an isolated test environment; do not clear site data or replace them. Participants enter only the sample values below. Do not request student names, roll numbers, contact details, universities/employers, real activities, evidence, signatures or backup files. Never use these synthetic entries for an actual internship submission.

Local-network HTTP can exercise core UI but not service-worker offline installation. For the offline task, use an owner-reviewed production HTTPS address or localhost on that device and wait for offline readiness. Publication is a separate owner action; do not change security settings, bypass certificate warnings or treat LAN HTTP as an HTTPS test.

Read this opening before proceeding:

> This is an optional test of an independent student tool using fictional sample records. We are testing the software, not you. It does not certify attendance or academic credit. You can skip any task or stop at any time. We will not record audio/video or collect your real internship information. May we retain brief, reviewed technical observations about what worked and what was difficult in the public project's documentation or issue tracker? You can review those notes and ask us to omit them before we finish.

If they decline participation, stop. If they decline retaining public technical notes, create no session record; they may still try the synthetic tasks without recorded feedback. Offer language clarification if useful and note assistance only when agreed, without assessing the participant. Do not recruit or contact anyone through automated tools as part of preparing this document.

## Debrief and feedback handling

Ask: What was hardest to find? Was any message unclear? Where would you keep a recovery copy? What would stop you using this for your own record organization? Record a short paraphrase, not a testimonial or a claim of endorsement. Read retained notes back and remove anything the participant declines to share.

Use the minimal record in [pilot feedback](pilot-feedback.md). A session code has no identity/contact mapping and is not a guarantee of anonymity. Keep only necessary technical observations; no recordings, real exports, identifying screenshots or raw personal quotations. If identifying information is volunteered, omit it from notes and reproduce any bug with synthetic data. Publish only reviewed de-identified technical findings; never place participant contact/scheduling information in Git or issues.

Stop on unexpected replacement, missing records, a privacy leak, an unusable recovery path or participant request. Preserve any existing valid data and the synthetic recovery copy; do not clear site data or retry stale writes automatically. A possible data-loss/privacy issue blocks further sessions pending reproduction and correction.

Triage findings as CRITICAL/HIGH/MEDIUM/LOW under [AGENTS.md](../AGENTS.md), separating observed defects, unverified reports and feature suggestions. Record the affected build/environment, synthetic steps, expected/actual behavior and verification evidence. Call a defect fixed only after a relevant check passes; keep unresolved reports/recommendations in the feedback record for later narrowly authorized work. No population-wide success rate or student validation claim follows from a small convenience sample. Sessions, fixes and publication must be reported as their actual separate outcomes.
